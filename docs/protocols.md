# 协议拓展：先把「协议」这个词拆开

一句话结论：**再多支持几种协议，都是「更大」；能证明同一份内容来自哪里、能从别处补上，才是「更深入」。**
所以这里不只是列一张「支持/不支持」表，而是给每种协议配三条判据：能不能续传、能不能多源、
校验值从哪来。没有第三条的协议，加了也只是「又多一个能下的地方」。

---

## 1. 现在真实支持什么（不是宣传口径）

| 寻址 | 传输 | 续传 | 校验来源 | 状态 |
|---|---|---|---|---|
| `http(s)://` 直链 | 分段（默认 5 路，1MB 一段）| Range + 位图 | 调用方 `--sha256` / 发布方 `.sha256` / TOFU | 已有 |
| `.m3u8` / `.mpd` 切片流 | 交给 ffmpeg 直取 | 按播放时长，片段级 | 由 ffmpeg 合并后算 | 已有 |
| `magnet:` / `.torrent`（v1、hybrid） | 多对等端 | 分块 | 种子自证（piece hash） | 已有 |
| `file:` 清单安装（`install`） | 本地/远程文件 + 落位 + chmod | — | 清单里写明 sha256 | 已有 |

明确拒绝并且会当场说清楚的：网盘（百度/阿里/夸克）、迅雷/电驴、BT v2-only、DRM 加密流。

## 1.5 礼貌条款（写进契约，不是道德倡议）

| 规则 | 落地 |
|---|---|
| 并发上限 | `-j` 默认 4–16；`SKYGET_MAX_PER_HOST` 默认 16（跨任务共享） |
| 限流退避 | 429/503 → 读 `Retry-After`（秒），夹到 ≤300s；无该头则 429 等 1.5s×n、503 等 0.3s×n |
| 重试次数 | 最多 4 次；`source.no_range` / `source.changed` / `verify.mismatch` 不重试 |
| 身份 | UA `skynet-download/<版本>`；不发 Referer；不用浏览器 cookie |
| 续传一致性 | `url + 总大小 + ETag` 三项全等才复用位图 |
| 拒绝 | `thunder://`、网盘分享页、`ed2k://`、NZB、DRM、站点抓取 |

## 2. 逐种候选：值不值得做

判据顺序：**能续传吗 → 能多源吗 → 校验值从哪来**。三条里只有一条的，收益基本等于「多一个地址」。

| 候选 | 它真正多给的东西 | 三条判据 | 成本 | 结论 |
|---|---|---|---|---|
| **多源同内容**（同一 sha256，N 个地址） | 一条线路断了/被限流，别的补上；总速度叠加 | 续传✓ 多源✓ 校验✓ | 中（引擎改造 + 一张恶意镜像的测试） | **做**。这是唯一能把「多协议」变成可验证能力的方向 |
| **Metalink**（RFC 5854） | 镜像列表 + 尺寸 + 多算法 hash，一份文件自带「从哪拿、拿到的对不对」 | 续传✓ 多源✓ 校验✓ | 低（XML 解析 + 复用上一行） | **做**，跟多源一起，成本几乎重叠 |
| **HTTP 认证/自定义头**（`--header`、Bearer、Basic、Cookie） | 私有 Git、S3/OSS 预签名链接、公司内网制品库 | 续传✓ 多源— 校验✓ | 低 | **做**。这不是新协议，是把已经能下的地址真的下下来 |
| **FTP / FTPS** | 老镜像站（部分 GNU/发行版归档）仍只给 FTP | 续传✓（REST）多源— 校验✓ | 中（新增依赖 + 被动模式 + TLS 分支） | **可做，排第三**。真需要时才做，别先做 |
| **WebDAV / Nextcloud** | 目录浏览 + 认证 | 续传✓ 多源— 校验— | 中 | **不做协议层**。用上面的 `--header` + 直链就够，PROPFIND 浏览是文件管理器的事 |
| **S3 / OSS / COS 直链** | 预签名 URL 就是 HTTPS | 续传✓ 多源— 校验✓ | 零 | **已经支持**（说清楚，别当成新功能吹） |
| **IPFS / gateway** | 网关地址就是 HTTPS | 续传✓ 多源✓ 校验（CID） | 低/高 | **不做原生**。走网关已经能下；接本地节点是另一个产品 |
| **BT v2-only** | 新一代种子 | 续传✓ 多源✓ 校验✓ | 取决于 librqbit | **看引擎**。v2-only 现在明确拒绝，等库支持再开 |
| **HLS + AES-128** | 大量视频源用这条 | 续传片段级 多源— 校验— | 低（ffmpeg 自带） | **先测再说**。ffmpeg 认 key URI，但没实测过就不要写「支持」 |
| **rsync://** | 增量同步 | — | 高 | **不做**。那是同步工具，不是下载 |
| **SFTP / SCP** | 远程文件 | 续传✓ | 中 | **不做**。要管密钥 = 换了一个产品 |
| **YouTube 一类站点抓取** | — | — | 高且易碎 | **不做**。那不是协议，是爬虫（且违反站点条款） |
| **ED2K / 迅雷 / 网盘** | — | — | 高 | **不做**。商业锁，假装支持比拒绝更糟 |

## 3. 如果真要做，先定三份东西再写代码

1. **源池规格**：N 个地址 → 一组分段任务怎么分派；某条源连不上/返回错内容/慢一半时怎么降权；
   全局只有一份 sha256 判据（分段级不校验，落地前整体校验）。
2. **失败判据表**：镜像撒谎（内容不同）、镜像截断、镜像限流、全部镜像都挂——四种情况各是什么结论、
   各留什么状态。**必须有反例测试**：一条源撒谎时，最终必须是「拒绝落地」而不是「碰巧用另一条源成功」。
3. **证据格式**：每条源分别贡献了多少字节、多少次失败，落到台账（`stats` 能算出来）。
   没有这列，「多源让我们更快」就只是感觉。

## 4. 四问（专家会做、但这次没要求的事）

**① 他们一定会先拆词。** 把「协议」拆成寻址 / 传输 / 证明三段。多支持一种协议通常只加寻址，
不加证明——而用户真正吃亏的地方往往是证明（下到了，但不知道对不对）。

**② 他们会从最原始的素材入手**，不是从「支持列表」入手：
真实响应头（`Content-Range`、`ETag`、`Last-Modified`、`Accept-Ranges` 到底怎么答的）、
`SHA256SUMS` / metalink 原文、种子的 piece hash、
失败那一刻的 TCP 状态（`SYN-SENT` 还是 `ESTABLISHED` 卡住）、
服务端日志里真正发出去多少字节（这是唯一能证明「续传真的续上了」的证据）。

**③ 方法上他们会做的事**：
- 每条协议写一张**能力矩阵**，而不是打勾：续传粒度、并发上限、校验来源、限流响应、错误语义。
- 用**恶意服务器**跑一致性测试（假 Range、假 Content-Length、截断、慢滴、429、重定向环、超长头）——
  我们的 `skyget selftest` 已经是这个形状，缺的是给新协议补同样的用例。
- **交叉校验**：同一内容分别从两条协议取，hash 一致才算数。这是「多协议」唯一真正的价值。
- 算**维护成本**：每多一种协议 = 一张必须长期测的矩阵 + 一个依赖的漏洞面。用「用户拿什么换」来否决它。

**④ 除了你我，谁还能证明结果对**：
- `skyget selftest` 的反例：一条镜像返回错内容 → 必须拒绝落地；一条镜像中途断 → 必须仍然完成。
- 服务端侧字节计数（我们自己的假服务器统计「第二趟只发了 2.00MB」就是这类证据）。
- 台账里每条源各自的字节数与失败次数（第三方拿到台账就能复核）。
- `git diff` + 那几条命令的退出码。
- 别人的 metalink 原文与官方 `SHA256SUMS`（外部锚点，不依赖我们两个）。

## 5. 建议的动手顺序（等你点头）

1. **Metalink 接入现有源池**：多源、坏镜像回退、内容错误拒绝落地已有；先写清单反例，
   再把 RFC 5854 读成现有 `sources`。
2. **`--header` / `--auth`**：一天的量，解锁私有源，风险低。
3. **FTP**：等真的有人只给 FTP 时再做。
4. 其余保持拒绝，并在手册里写清理由（已经在 `MANUAL.md` §7）。
